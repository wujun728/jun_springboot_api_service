- **项目名称**: {{PROJECT_NAME}}

## 你必须严格按顺序执行以下步骤：

### STEP 1: 了解当前状态（必做！）

在做任何事情之前，先了解情况：

1. 运行 `pwd` 确认工作目录
2. 读取 `{{PROGRESS_FILE}}`，了解之前完成了什么工作
3. 运行 `git log --oneline -10`，查看最近的提交记录
4. 运行 `git status`，确认工作目录是否干净
5. 如果存在 `{{INIT_SCRIPT}}`，阅读它了解如何运行项目

### STEP 2: 验证环境健康

运行基础检查确保环境正常：

1. 运行编译命令: `{{BUILD_COMMAND}}`
2. 如果编译失败，**优先修复编译错误**，不要开始新功能
3. 如果有运行中的服务，确认它能正常响应

**关键原则**: 如果环境有问题，先修复问题，再考虑新功能。在损坏的基础上添加新功能只会让情况更糟。

### STEP 3: 阅读功能列表

读取 `{{FEATURE_LIST}}`，了解：
- 哪些功能已完成（`passes: true`）
- 哪些功能待实现（`passes: false`）
- 各功能之间的依赖关系

### STEP 4: 选择一个功能来实现

查看 `{{FEATURE_LIST}}`，找到**优先级最高**且 `passes: false` 的功能。

选择规则：
1. 该功能的所有 `dependencies` 都已经 `passes: true`
2. 在满足条件的功能中，选择 `priority` 值最小的
3. 如果优先级相同，选择 `id` 最小的

**一次只实现一个功能。** 在本次会话中完美地完成一个功能，远比潦草地处理多个功能更有价值。后续会话会继续处理剩余功能。

### STEP 5: 实现功能

针对选中的功能：

1. 仔细阅读功能描述和验证步骤
2. 规划实现方案（在脑中，不需要写出来）
3. 编写代码实现
4. 保持代码质量：
   - 遵循项目已有的代码风格
   - 添加必要的注释
   - 处理异常情况
   - 不引入不必要的复杂度

**Java 项目编码规范：**
- 使用项目已有的包结构
- Entity/DTO/VO 分层清晰
- Service 层包含业务逻辑，Controller 层只做参数转换和调用
- 使用 @Autowired 或构造器注入
- 异常使用全局异常处理器
- API 遵循 RESTful 规范

**前端编码规范：**
- 组件命名使用 PascalCase
- 遵循已有的状态管理方式
- 样式与逻辑分离
- 响应式设计

### STEP 6: 验证功能

按照 `feature_list.json` 中该功能的 `steps` 逐条验证：

1. 先运行编译: `{{BUILD_COMMAND}}`，确认编译通过
2. 如果有测试: 运行 `{{TEST_COMMAND}}`
3. 按 steps 中的每一步手动验证
4. **只有当所有验证步骤都通过时**，才能进入下一步

如果验证失败：
- 修复代码
- 重新验证
- 如果本次会话内无法修复，记录问题但**不要将功能标记为通过**

### STEP 7: 更新 feature_list.json（请务必谨慎！）

**你只能修改一个字段: `passes`**

在完成验证后，将该功能的状态从:
```json
"passes": false
```
改为:
```json
"passes": true
```

**严禁以下行为：**
- ❌ 删除任何功能条目
- ❌ 修改功能描述（description）
- ❌ 修改验证步骤（steps）
- ❌ 修改优先级（priority）
- ❌ 修改依赖关系（dependencies）
- ❌ 添加新功能

删除或编辑测试是不可接受的，因为这可能导致功能缺失或存在缺陷。

### STEP 8: Git 提交

将所有更改提交到 Git：

```bash
git add .
git commit -m "feat(F0XX): 功能描述的简要总结"
```

提交信息格式：
- `feat(ID): 描述` — 新功能
- `fix(ID): 描述` — Bug 修复
- `refactor(ID): 描述` — 重构

### STEP 9: 更新进度文件

在 `{{PROGRESS_FILE}}` **末尾追加**（不要覆盖已有内容）：

```

- 实现了: [功能描述]
- 修改的文件: [文件列表]
- 测试结果: [通过/失败]
- Git 提交: [commit hash]
- 状态: [完成/部分完成/失败]
- 下一步建议: [给下一个会话的建议]
```

### STEP 10: 最终验证

在结束前做最后检查：
1. `git status` — 确认工作目录干净
2. `{{BUILD_COMMAND}}` — 确认整个项目仍可编译
3. 确认没有引入新的编译警告或错误

## 核心原则

1. **小步快跑**: 一次只做一个功能。做完、测完、提交。
2. **干净状态**: 离开时环境必须是可编译的，代码是已提交的。
3. **诚实标记**: 只有真正通过验证的功能才标记为 `passes: true`。
4. **不要贪多**: 完成一个功能就是本次会话的成功。还有后续会话。
5. **先修后建**: 如果发现已有代码有问题，先修复，再实现新功能。
6. **留下痕迹**: 通过 Git 提交和进度文件，让下一个会话能快速了解状况。
